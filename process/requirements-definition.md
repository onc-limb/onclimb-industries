# 02. 要件定義

## 0. 一行定義

このフェーズは「**01 で合意した障害の除去に対して何を作れば目的を満たすか——依頼事項への実現可否の判断と、スコープ（やること・やらないこと）・受け入れ条件・非機能要件——を、依頼者と作り手が合意した状態**」を確定させる。

要件とは依頼者の要望リストではない。**依頼事項 + 作り手の実現可否判断の、合意事項**である。
可否を判断せずに要望を書き写した文書は要件定義書ではなく、御用聞きのメモである。

## 1. 扱う抽象度

### 扱うもの

- **企画の確認** — 目的・企画のゴールを 5 分で説明できる状態にする。ここが未定なら**黄色信号**であり、01 / 企画の整理に差し戻す
- **全体像** — 利用者がシステムを通じて行うこと・達成できることの一覧と時系列（ユーザーストーリーマッピング）
- **業務の構造** — 業務で起きる出来事（ドメインイベント）、それを起こす操作と人、扱われるエンティティ・集約（イベントストーミング。概念データモデルはここで表現する）
- **UI の当たり** — 主要画面のワイヤーフレームと画面遷移。**実データ（相当）で**見せる
- **ユースケース** — 画面を伴わないもの（集計・連携・バッチ・通知）も含めた一覧
- **実現可否と代替案** — 要望ごとの可否。否の場合は理由（能力・予算・現実的障害）と代替案
- **受け入れ条件** — どうなっていたら受け取れるか（ユースケース単位・観測可能な形）
- **非機能要件** — 性能・セキュリティ・可用性・運用の要求レベル
- **リリースの切り方** — 最初に届ける最小の縦切り（マップのスライス）

### 扱わないもの（他フェーズの領分）

| 扱わないもの | どのフェーズの領分か |
| --- | --- |
| 目的・障害・成功基準の再定義 | 01 要求分析（未定なら差し戻す。ここで発明しない） |
| 技術選定・構成・非機能の実現方式 | 03 アーキテクチャ設計 |
| 物理 DB 設計（DB の種類・テーブル定義・インデックス・イベントソーシング採否） | 03 / 04 |
| クラス設計・API 仕様の詳細 | 04 詳細設計 |
| ビジュアルデザイン（配色・装飾・トンマナ） | 04 / 実装 |
| 工数・見積・スケジュール | 提案（`friday-proposal-generator`） |

> ここに書いたものが会話・ドキュメントに出てきたら、このフェーズでは**脱線**として扱う。
> 例外は実現可否の判断に必要な範囲の技術的あたり（「この構成なら現実的」レベル）。
> 判断根拠として持つのはよいが、成果物に技術詳細を書き始めたら 03 へ退避する。

## 2. 中心の問い

| # | 問い | なぜこれを問うか |
| --- | --- | --- |
| Q1 | この企画は 5 分で説明できる状態か | できなければ要件のゴール（UI・機能・データ）は定義できない。黄色信号 |
| Q2 | 利用者は誰で、システムを通じて何を行い、何を達成できるか | 全体像が無いと、個別の要望の位置づけと漏れが分からない |
| Q3 | 業務ではどんな出来事が起き、誰のどの操作がそれを起こすか | 画面の都合ではなく業務の構造からデータと機能を導くため |
| Q4 | 各画面で利用者は何を見て、何をするか。実データで見せたか | 内部で動いていると口で言っても伝わらない。ダミーデータではイメージできない |
| Q5 | UI に現れない機能（集計・連携・バッチ・分析）は何か | 企画者の「あって当たり前」は表に出さないと伝わらず、後から発覚する |
| Q6 | 各要望は実現できるか。できないなら理由と代替案を伝えたか | 可否と理由を明確に伝えないことが不信感の主因 |
| Q7 | 今回やらないことは何か | やらないことの無いスコープは、まだ判断していない |
| Q8 | どうなっていたら受け取れるか | 受け入れ条件の不在は検収時の揉め事の予約 |
| Q9 | 性能・セキュリティ・運用は、どのレベルを要求されているか | 非機能は要望として口に出ないが、外すと完成後に「使えない」となる |
| Q10 | 最初のリリースで届ける最小の縦切りはどこか | 全部入りの初回リリースは破綻の予約。マップを横に切る |

> Q1 で詰まったら先に進まない。ここで粘るより 01 / 企画に戻る方が早い。
> Q6 は「できません」で止めない。理由と代替案までがワンセット。

## 3. 集める情報のフォーマット

このフェーズの成果物は次の 6 点。ワイヤーフレームの形式は TBD。

| # | 成果物 | 型 |
| --- | --- | --- |
| 1 | 企画書サマリー | 5 分で読める 1 枚（目的 / 誰の何を解決 / 企画のゴール / 制約） |
| 2 | ユーザーストーリーマッピング | 活動の時系列（バックボーン）× 優先度。リリーススライス入り |
| 3 | イベントストーミング | イベント → コマンド → アクター → エンティティ・集約（概念データモデルを含む） |
| 4 | ワイヤーフレーム | 主要画面 + 画面遷移。実データ相当を流し込む（形式 TBD） |
| 5 | ユースケース一覧 | 下記テンプレート。画面を伴わないものを含む |
| 6 | 要件定義書 | 下記テンプレート。1〜5 を束ねる合意文書 |

```markdown
# 要件定義書: <案件名>

日付: YYYY-MM-DD / 合意者: <依頼者側> / <作り手側>
前提資料: 要求分析(01) / 企画書サマリー / USM / イベントストーミング / ワイヤーフレーム / ユースケース一覧

## ゴール
- 解決する課題（01 から転記）:
- 達成の判定指標（01 の成功基準をシステムの言葉に翻訳したもの）:

## スコープ
### やること（ユースケース一覧の採用分を参照）
### やらないこと
| 項目 | やらない理由 | 再検討の条件 |
| --- | --- | --- |

## 要望と実現可否
| 要望 | 可否 | 否の理由 / 代替案 | 依頼者の判断 |
| --- | --- | --- | --- |

## 受け入れ条件
| ユースケース | 条件（観測可能な形） | 確認方法 |
| --- | --- | --- |

## 非機能要件
| 分類 | 要求レベル | 根拠 |
| --- | --- | --- |
<!-- 性能 / セキュリティ / 可用性 / 運用・保守 / データ量の見込み -->

## 前提条件・制約（01 から転記 + このフェーズで判明した分）

## 未確定・持ち越し
| 事項 | 持ち越し先フェーズ | 期限 |
| --- | --- | --- |
```

```markdown
# ユースケース一覧: <案件名>

| ID | ユースケース（誰が / 何を / 何のため） | 画面 | 発生契機 | 優先度 | 受け入れ条件へのリンク |
| --- | --- | --- | --- | --- | --- |
<!-- 画面欄が「なし」の行（バッチ・連携・通知・集計）を必ず点検する。ゼロなら Q5 に戻る -->
```

### 各項目の書き方の基準

| 項目 | 良い記述 | 悪い記述 |
| --- | --- | --- |
| ユースケース | 経理担当が月次の請求一覧を CSV で出力する（月次締めのため） | 出力機能 |
| 実現可否 | リアルタイム同期は予算内では不可。5 分間隔のバッチ同期なら可、締め業務には支障なし | 検討します |
| 受け入れ条件 | 請求一覧画面で 2026-06 を指定すると、会計システムと同額の合計が表示される | 正しく表示される |
| 非機能 | 月末ピーク時 20 人同時利用で一覧表示 3 秒以内 | サクサク動く |
| やらないこと | 過年度データの移行はやらない（現行システムを参照運用で残すため） | （記載なし） |

> **推測には必ず `(推測)` を付ける。** 依頼者に確認した合意と、自分が埋めた仮説を混ぜない。

## 4. 完了条件

- [ ] 企画書サマリーを依頼者が読み、内容の認識が一致している（5 分で説明できる状態）
- [ ] USM に利用者の活動が時系列で並び、最初のリリーススライスが引かれている
- [ ] イベントストーミングが主要な業務フローを覆い、エンティティ・集約が抽出されている
- [ ] 主要画面のワイヤーフレームを**実データ相当**で依頼者に見せ、フィードバックを反映した
- [ ] ユースケース一覧に**画面を伴わないユースケース**が点検済みで載っている
- [ ] すべての要望に可否が付き、否には理由と代替案、依頼者の判断が記録されている
- [ ] やらないことが 1 つ以上、理由付きで書かれている
- [ ] 受け入れ条件が観測可能な形でユースケースに紐づいている
- [ ] 非機能要件に要求レベルと根拠が書かれている
- [ ] 要件定義書に依頼者・作り手双方の合意が記録されている
- [ ] **成果物に技術選定・物理 DB 設計が書かれていない**（レール検査）

## 5. アンチパターン

| 兆候（会話・文書に現れる形） | 何が起きているか | 引き戻し方 |
| --- | --- | --- |
| 目的・企画のゴールが曖昧なまま要件を書き始めている | 黄色信号。ゴールの無い要件は合意のしようがない | 01 / 企画の整理に差し戻す |
| 「お任せします」のまま進んでいる | お任せでは詳細まで詰まらない。後で「思っていたのと違う」になる | 具体案を 2 つ持って行き、どちらが近いかから詰める |
| 内部の仕組みを口頭で説明して合意した気になっている | 動いているものの想像が双方で食い違っている | 何はともあれ UI（ワイヤーフレーム）を先に見せる |
| ダミーデータの画面でレビューしている | 依頼者は自分のデータでしかイメージできない | 実データ（相当）を流し込んで見せ直す |
| 「できません」だけ伝えている | 理由と代替案の無い否は不信感になる | 理由（能力・予算・現実的障害）と代替案をセットで返す |
| 機能名の羅列になっている（誰が・何のためが無い） | 要望の丸写し。価値とスコープの判断ができない | ユースケースの形（誰が / 何を / 何のため）に書き直す |
| 画面一覧 = 機能一覧になっている | UI に現れない機能（バッチ・連携・集計）が漏れている | ユースケース一覧の「画面なし」行を点検する |
| 全機能が初回リリースに入っている | スライスの放棄 | 「最初の 1 ヶ月使うのに無くても困らないものはどれか」 |
| 受け入れ条件が「満足いただけたら」 | 検収の基準が無い | ユースケースごとに観測可能な条件へ落とす |
| テーブル定義や DB 製品の議論を始めている | フェーズの先食い。概念より下は 03 / 04 の領分 | エンティティ・集約（概念）までで止めて退避する |
| 要望が増え続けている | やりたいことリストとスコープが未分離 | リストに退避し、今回スライスに入れるかだけ判断する |

## 6. 相手との会話

主に向き合う相手: **クライアント**（依頼者。および実際に使う利用者）

### 引き出す問いかけ

- 「この画面、普段お使いの実際のデータだとどう見えるか、入れてみました。違和感はどこですか」
- 「この操作の裏で、画面に出てこないけれど起きていてほしいことはありますか」
- 「これは技術的に難しいのですが、代わりに◯◯という方法なら、目的は満たせそうですか」
- 「最初のリリースで、無くても 1 ヶ月は困らないものはどれですか」
- 「これがどうなっていたら、受け取れますか」
- 「同時に何人くらいが使いますか。一番多い時期はいつですか」
- 「このデータが消えたら、業務はどれくらい止まりますか」

### 言い換え・地雷

| 相手の言葉 | そのまま受けない理由 | 返す問い |
| --- | --- | --- |
| 「お任せします」 | 詳細が詰まらないまま進み、完成後に食い違いが露呈する | 「2 案作りました。どちらが近いですか」 |
| 「普通でいいです」 | 「普通」の中身が双方で違う | 「普段お使いの◯◯だと、どの動きが普通ですか」 |
| 「それはあって当たり前だと思っていた」 | 暗黙知が表に出ていなかった | ユースケース一覧を見せ「この表に無いものは作られません」と確認する |
| 「全部必要です」 | スコープ判断の放棄 | 「順番をつけるとしたら、最初の 3 つはどれですか」 |
| 「ついでにこれもできますか」 | スコープの膨張 | 「リストに追加します。今回のリリースに入れるかは優先度で決めましょう」 |
| 「データは大体こんな感じです」 | 実データと乖離していると UI もモデルも歪む | 「実際のファイルを 1 ヶ月分いただけますか（マスキング可）」 |
| 「速ければ速いほどいい」 | 非機能が要求レベルにならない | 「何秒を超えると業務に支障が出ますか」 |

## 7. 入出力

- **入力**（01 要求分析から受け取るもの）:
  1. 今回取り除く障害（と、やらない障害）
  2. 成功の判定基準
  3. 動かせない制約
  - 加えて企画書（あれば）。無ければ企画書サマリーの作成を通じて依頼者と一緒に固める
- **出力**（03 アーキテクチャ設計へ渡すもの）:
  1. 要件定義書（スコープ・受け入れ条件・**非機能要件**が 03 の設計制約になる）
  2. イベントストーミングの成果物（エンティティ・集約が 03 / 04 のデータ設計の入力になる）
  3. ユースケース一覧・USM・ワイヤーフレーム（構造とリリース計画の根拠）
  - 物理 DB 設計（DB の種類・イベントソーシング採否を含む）はここでは決めず、03 / 04 に持ち越す
- **出力が欠けたまま進めた場合に起きること**:
  - 受け入れ条件が無い → 検収時に「思っていたものと違う」で揉める
  - やらないことが無い → スコープが膨張し続け、リリースが定まらない
  - イベントストーミング（概念データモデル）が無い → データ設計が画面の都合で歪み、後の機能追加で作り直しになる
  - 画面を伴わないユースケースが漏れる → バッチ・連携が後から発覚し、構成ごと手戻りする
  - 非機能要件が無い → 03 で根拠なく構成を選び、完成後に性能・運用で「使えない」となる
