# 01. 要求分析

## 0. 一行定義

このフェーズは「**クライアントが達成したい状態と、それを妨げている障害の因果構造を双方が同じ言葉で言えるようにし、今回どの障害を取り除くかの合意**」を確定させる。

手段（何を作るか）には一切触れずに終える。触れた時点でこのフェーズは失敗している。

## 1. 扱う抽象度

### 扱うもの

- **目的** — 達成したい状態。「なぜ今か」を含む
- **障害の因果構造** — あるべき姿を妨げているものと、それが起きている原因
- **影響** — 障害によって失われている量（時間・金額・頻度・人数）と、被っている人
- **ステークホルダー** — 誰が困り、誰が困っていないか。決裁者は誰か
- **制約** — 動かせない前提（期限・予算・体制・法規制・既存システムの存在）
- **スコープ判断** — 今回どの障害を取り除き、どれをやらないか
- **成功の判定基準** — 取り除けたとどう判定するか（測り方と測る人まで）

### 扱わないもの（他フェーズの領分）

| 扱わないもの | どのフェーズの領分か |
| --- | --- |
| どんな機能を作るか | 02 要件定義 |
| 画面・UI・操作フロー | 02 要件定義 / 04 詳細設計 |
| 技術選定・構成 | 03 アーキテクチャ設計 |
| データ構造・テーブル | 04 詳細設計 |
| 既存システムの実装詳細 | 03 / 04（必要になった時点で調査） |
| 工数・見積・スケジュール | 方向性合意後の提案（`friday-proposal-generator`） |
| 「できる / できない」の技術的判断 | 03 アーキテクチャ設計 |

> ここに書いたものが会議・資料に出てきたら、このフェーズでは**脱線**として扱う。
> ただしクライアント側が口にするのは自然なので、禁止するのではなく「メモに退避して目的に戻す」。
> 禁止対象は**自分が扱いに行くこと**。

## 2. 中心の問い

| # | 問い | なぜこれを問うか |
| --- | --- | --- |
| Q1 | 誰が、どういう状態になりたいのか | 目的が状態で語られないと、達成判定ができない |
| Q2 | なぜ今なのか。去年でも来年でもなく | 今やる理由が無い案件は、途中で優先度が落ちて止まる |
| Q3 | それを妨げているものは何か。なぜそれが起きているのか | 現象で止まると、現象だけ潰して問題が残る |
| Q4 | 放置すると何が起きるか。今いくら損しているか | 影響の量が無いと、優先順位も投資判断もできない |
| Q5 | 今はどう凌いでいるか。なぜそれでは足りないのか | 回っている業務を壊さないため。回避策の存在は制約になる |
| Q6 | 誰が困り、誰が困っていないか | 困っていない人が抵抗勢力になる。使われないシステムの主因 |
| Q7 | 今回どの障害を取り除き、どれをやらないか | 全部やる合意は、破綻の予約 |
| Q8 | 取り除けたとどう判定するか | 検収時の揉め事はほぼ全部ここの不在から出る |
| Q9 | 動かせない制約は何か | 制約を後から知ると、方向性ごとやり直しになる |

> Q3 は 1 回で止めない。現象 → 原因 → その原因、と最低 2 段掘る。
> Q7 は「やらないもの」を必ず 1 つ以上言わせる。ゼロなら、まだ判断していない。

## 3. 集める情報のフォーマット

```markdown
# 要求分析: <案件名>

日付: YYYY-MM-DD / 同席者: / 情報源: (ヒアリング / 資料 / 推測)

## 目的
- 達成したい状態:
- なぜ今:
- 発案者:
- 決裁者:

## 問題の因果構造

あるべき姿: <観測可能な状態>
└ 障害1: <何が妨げているか>
   └ 原因: <なぜそれが起きているか>
      └ さらに原因: <掘れる限り>
   ├ 影響: <量・頻度・誰に>
   └ 現行の回避策: <今どう凌いでいるか / なぜ足りないか>
└ 障害2: ...

## ステークホルダー

| 誰 | 立場 | この問題での利害 | 変化への態度 | 直接聞いたか |
| --- | --- | --- | --- | --- |

## 制約

| 種類 | 内容 | 動かせるか | 出所 |
| --- | --- | --- | --- |

## 今回のスコープ判断

| 障害 | 今回取り除くか | 理由 |
| --- | --- | --- |

## 成功の判定基準

| 指標 | 現在値 | 目標値 | 測り方 | 測る人 | いつ測るか |
| --- | --- | --- | --- | --- | --- |

## 未確定・仮説

| 事項 | 現時点の仮説 | 確かめ方 | いつまでに |
| --- | --- | --- | --- |
```

### 各項目の書き方の基準

| 項目 | 良い記述 | 悪い記述 |
| --- | --- | --- |
| あるべき姿 | 月次締めを 3 営業日で終える | 業務を効率化したい |
| 障害 | 実績集計に 5 営業日かかる | システムが古い |
| 原因 | 3 部署が別様式の Excel を手で統合している | 属人化している |
| 影響 | 経理 2 名 × 月 40h / 報告遅延で意思決定が 1 ヶ月遅れる | 現場が大変 |
| 成功基準 | 締めのリードタイム 5 → 2 営業日（経理課長が月次で計測） | 使いやすくなる |
| 制約 | 4 月の期首から新体制。3 月末までに稼働（社長決裁済み） | なるべく早く |

> **推測には必ず `(推測)` を付ける。** ヒアリングで聞いた事実と、自分が埋めた仮説を混ぜない。
> 混ざった瞬間、この資料はクライアントと共有できなくなる。

## 4. 完了条件

- [ ] あるべき姿が、観測可能な状態として 1 文で書けている
- [ ] 障害が最低 1 つ、原因まで 2 段以上掘られている
- [ ] 各障害の影響が、量（時間・金額・頻度・人数）で書けている
- [ ] 現行の回避策と、それでは足りない理由が書けている
- [ ] 今回取り除く障害と、**やらない障害**が分かれており、やらない理由がある
- [ ] 成功の判定基準に、測り方と測る人といつ測るかが入っている
- [ ] 決裁者が特定されており、その人がこの因果構造に同意している
- [ ] 困っている当人に直接聞けている（伝聞のみの障害は「未確定」に落とす）
- [ ] 未確定事項が、確かめ方と期限つきでリストになっている
- [ ] **資料に「何を作るか」が一切書かれていない**（レール検査）

## 5. アンチパターン

| 兆候（会話・文書に現れる形） | 何が起きているか | 引き戻し方 |
| --- | --- | --- |
| クライアントが「◯◯システムが欲しい」から話し始める | 手段が目的化。既に解を持っている | 「それがあると、今の何が変わりますか」 |
| 自分が画面・技術の話を始めている | 実装可能性の安心を先に取りに行っている。目的の解像度が上がる前に手段が固まる | メモに退避して目的に戻る |
| 「効率化」「見える化」「DX」のまま合意している | 合意したのは言葉だけ。中身は食い違ったまま | 「それは誰の何時間が減ることですか」 |
| 障害が 1 段で止まっている（「Excel だから」） | 現象であって原因ではない | 「なぜ Excel だと 5 日かかるのですか」をあと 2 回 |
| 影響が「大変」「困っている」で量が無い | 優先順位も投資判断もできない | 「月に何時間ですか」「それが何人ですか」 |
| 全ての障害を今回やることになっている | スコープ判断の放棄 | 「1 つだけ落とすとしたら、どれですか」 |
| 困っている当人が同席していない | 要求が伝聞と推測で組まれている | 現場ヒアリングを次の条件にする |
| 成功基準が「クライアントの満足」 | 検収時に必ず揉める | 「何がどうなっていたら成功と言えますか」 |
| 現行の回避策を聞いていない | 既に回っている業務を壊す方向に進む | 「今はどう凌いでいますか」 |
| 決裁者が会話に一度も出てこない | 合意しても覆る | 「これは最終的にどなたが決めますか」 |
| 自分が納得して喋る時間が長くなっている | 聞くフェーズなのに提案している | 発言比率を意識的に戻す |

## 6. 相手との会話

主に向き合う相手: **クライアント**（決裁者と、困っている当人の両方）

### 引き出す問いかけ

- 「これがうまくいったら、半年後、何がどう変わっていますか」
- 「なぜ今やるのですか。去年ではなく」
- 「今はどう凌いでいますか」
- 「一番困っているのは誰ですか。その人は何と言っていますか」
- 「やらなかったら、何が起きますか」
- 「月に何時間ですか / 月に何回ですか」
- 「この中で 1 つしか解決できないとしたら、どれですか」
- 「これは最終的にどなたが決めますか」

### 言い換え・地雷

| 相手の言葉 | そのまま受けない理由 | 返す問い |
| --- | --- | --- |
| 「今のをそのまま作り直して」 | 現行の問題ごと複製することになる。目的が語られていない | 「今のもので、残したい部分と捨てたい部分はどこですか」 |
| 「使いやすくしたい」 | 誰にとっての何が、測れない | 「誰が、どの操作で詰まっていますか」 |
| 「AI で何かできない？」 | 手段先行。目的が空 | 「今、一番時間を取られている作業は何ですか」 |
| 「他社もやっているので」 | 自社の目的が無い。導入しても効果が出ない | 「御社で同じことをやると、何が良くなりますか」 |
| 「将来的には全部やりたい」 | スコープが無限になり、方向性が定まらない | 「最初の 3 ヶ月で 1 つだけ変えるなら、どれですか」 |
| 「予算はまだ決まっていない」 | 方向性合意の前提が欠けている | 「決めるのはどなたで、いつごろの想定ですか」 |
| 「現場は特に困っていないと思う」 | 決裁者の推測。現場の実態が不明 | 「現場の方に直接お話を伺えますか」 |

## 7. 入出力

- **入力**: 引き合い・相談・RFP・既存資料。この時点では相手の言葉のままでよい
- **出力**: 「3. 集める情報のフォーマット」で埋めた 1 本のドキュメント。
  中でも次の 3 点が、02 要件定義の前提になる
  1. 今回取り除く障害（と、やらない障害）
  2. 成功の判定基準
  3. 動かせない制約
- **出力が欠けたまま進めた場合に起きること**:
  - 取り除く障害が未合意 → 要件定義でスコープが膨張し続け、見積が出せない
  - 判定基準が未合意 → 検収時に「思っていたものと違う」で揉める
  - 制約が未把握 → 方向性ごとやり直しになる
  - 困っている当人に未確認 → 完成しても使われない

## 関連

- 自分の頭の中を整理する段階（クライアントと話す前 / 話した後）は `karen-problem-essence-organizer` が
  課題発見 → 課題整理 → 解決定義 → 手段検討の 4 フェーズで壁打ちする。このファイルは
  **その整理結果をクライアントと共有できる形に固定するための型**にあたる。
- 方向性合意の後、提案書・見積に落とすのは `friday-proposal-generator`。
