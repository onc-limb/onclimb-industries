# process — 開発フェーズごとの考え方のレール

開発の各フェーズで「どの抽象度のものを扱い、何を問い、どういう情報が揃ったら次に進めるか」を
フェーズごとに定義した知識ディレクトリ。`architecture/` が**設計の中身**の正本であるのに対し、
ここは**進め方（どのフェーズで何を考えるか）**の正本。

## 何のためにあるか

1. **クライアントとのコミュニケーションの土台** — 何を聞き、何をまだ聞かないかの基準にする
2. **AI 添削の基準** — 自分の書いた資料・議事録・発言をこのレールと突き合わせて、
   フェーズの抽象度を踏み外していないかを指摘させる
3. **自分の思考の脱線検知** — 手段先行・目的喪失に気づくためのチェックポイント

## 1 ファイルの構造

全フェーズ [`_TEMPLATE.md`](_TEMPLATE.md) の章立てに従う。章立てを揃えるのは、
AI 添削が「1. 扱う抽象度 → 扱わないもの」の表と突き合わせて脱線を機械的に検出できるようにするため。

## 使い方

### クライアントと話す前

該当フェーズの「2. 中心の問い」と「6. 相手との会話」を開き、聞くことと聞かないことを決めてから臨む。

### 話した後 / 資料を書いた後

議事録・メモ・資料と該当フェーズのファイルを AI に渡し、次を指摘させる。

- 「1. 扱わないもの」に踏み込んでいる箇所
- 「2. 中心の問い」のうち答えが埋まっていない問い
- 「5. アンチパターン」の兆候に該当する記述
- 「4. 完了条件」のうち満たしていない項目

### 育て方

実案件で「レールを外れた」「この問いが足りなかった」と気づいたら、該当フェーズのファイルに追記する。
特に「5. アンチパターン」は実体験でしか埋まらないので、失敗のたびに 1 行足す。
