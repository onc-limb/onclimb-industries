# 構成図の流儀（育成中）

cloud-infra-engineer が構成図を描くときの規約。**このファイルが正本**。
案件で決めた流儀は末尾の「決定ログ」に追記して育てる。

構成図は必ず 4 点セットで出す:
**(1) Mermaid 図 / (2) コンポーネント表 / (3) 設計意図注記 / (4) 非エンジニア向け説明**

## 1. Mermaid 図

- 記法は `graph TB`（上から下: 利用者 → 入口 → アプリ → データ）。
- **subgraph = ネットワーク境界**に限定して使う（VPC / サブネット public・private /
  マネージドサービス領域）。論理グルーピングのための subgraph 乱用はしない。
- ノードラベルは `役割<br/>(サービス名)` の 2 行（例: `アプリ実行<br/>(Cloud Run)`）。
  役割が先、サービス名は括弧。非エンジニアが役割だけ読んでも流れを追えるようにする。
- 矢印には主要な通信内容を書く（`-->|HTTPS|`、`-->|SQL|` 等。全矢印でなくてよい）。
- インターネット・利用者・外部 SaaS は VPC の subgraph の外に置き、境界を跨ぐ線が
  どこかを一目で分かるようにする。
- 色分け（classDef）: public に露出するもの / private なもの / マネージドサービス の
  3 分類を初期値とする。

## 2. コンポーネント表

| コンポーネント | リソース種別 | 役割 | 冗長化 | ネットワーク配置 |
|---|---|---|---|---|

Terraform が既にある場合は「Terraform リソース（アドレス）」列を足して図との対応を取る。

## 3. 設計意図注記

図の直後に「なぜこの構成か」を表で残す。**図は What、注記は Why** の分担。

| 選択 | 理由 | 根拠（出典 URL・取得日 / ASSUMPTION） |
|---|---|---|

- コードや会話から読み取れない意図は創作せず **(要確認)** と書いてユーザーに確認する。
- 不採用にした代替案があれば「〜ではなく〜にした」の形で 1 行残す。

## 4. 非エンジニア向け説明

図の下に固定 3 項目、各 2〜4 文の平易な日本語で書く。

- **この構成でできること** — 利用者から見た振る舞い。サービス名を使わずに書く
  （必要なら「受付窓口にあたるもの」のような役割の言い換えを使う）。
- **お金がかかる場所** — 常時かかるもの / 使った分だけのもの の区別。金額は概算と明記。
- **壊れたらどうなるか** — どこが止まると何ができなくなるか。自動で復旧するのか、
  人の対応が要るのかを書く。

言い換えに迷う専門用語が出たら jarvis-allspeak の言い換え DB を参照してよい
（無ければ自力で平易化し、用語をキューに入れるか一言提案する）。
