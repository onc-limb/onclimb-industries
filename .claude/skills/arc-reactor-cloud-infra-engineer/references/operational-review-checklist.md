# 可用性・運用レビューチェックリスト

フロー D で使う可用性・運用観点の正本。セキュリティ観点は
`arc-reactor-infra-architecture-designer/references/security-review-checklist.md` を使う。
全観点を確認し、指摘が無い観点も「確認済み」として列挙する。

## 単一障害点 (SPOF)

- 止まるとサービス全体が止まるコンポーネントはどれか。それは意図した割り切りか
- AZ 障害で何が止まるか（マルチ AZ の要否は可用性要件と照らして判断する）
- NAT Gateway / 踏み台など「地味な単一点」を見落としていないか

## バックアップ / DR

- データストアごとにバックアップの取得有無・頻度・保持期間が決まっているか
- **リストア手順が存在するか**（バックアップがあってもリストア未検証なら指摘する）
- RTO / RPO の目安が要件と合っているか（未定義なら ASSUMPTION として明示する）
- 削除保護（deletion protection / スナップショット最終取得）が本番データストアに有るか

## 監視・アラート

- 死活・エラー率・レイテンシ・飽和（CPU / メモリ / ディスク / 接続数）の basic 4 が見えるか
- アラートの通知先が決まっているか（ダッシュボードだけで誰も気づかない構成になっていないか）
- ログの保管先と保持期間が決まっているか（コストと両睨み）

## スケール・クォータ

- トラフィック増に対しどこから詰まるか（スケール手段が自動か手動か）
- サービスクォータ・上限（同時実行数・接続数・API レート）に当たる見込みはないか。
  怪しい上限値は公式ドキュメントで裏取りする
- スケールしない依存先（外部 API・DB 接続数）に対する保護（キュー・レート制限）が有るか

## コスト暴走

- 従量課金で暴走し得る箇所（NAT / egress 通信・ログ取り込み・サーバレス無限リトライ・
  オートスケール上限なし）に歯止めが有るか
- 予算アラート（AWS Budgets / Cloud Billing budget）の設定を案内したか
- 開発環境の消し忘れ・夜間停止の運用が決まっているか

## 運用経路

- デプロイ経路が決まっているか（CI/CD か手動か。手動なら手順書の在処）
- Terraform の state と実環境の drift をどう検知・解消するか（コンソール手作業の扱い）
- 定期メンテナンス（証明書更新・エンジンバージョン EOL・パッチ）を誰がいつやるか。
  EOL 日付に関わる指摘は公式ドキュメントで裏取りする
- 障害時に人が入る経路（踏み台 / SSM Session Manager / IAP）が確保されているか

## 出力形式

- 指摘表: 観点 / 該当コンポーネント（file:line があれば添える）/ 重大度 High・Mid・Low / 対策案
- 確認済み観点の列挙（指摘なしも含む）
- 免責: 専門の SRE アセスメント・セキュリティ監査の代替ではない旨を毎回明記する
